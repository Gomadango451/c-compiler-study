■ アセンブリ命令の読み方(Intel記法)

【基本の形】
  命令  行き先, 元
  例) mov rax, 42   → rax = 42
  ・左が「行き先」、右が「元」(Cの代入文 左 = 右 と同じ向き)
  ・1行に命令は1つ

【オペランド(命令の対象)の3種類】
  レジスタ   rax, rdi など        → CPU内の変数のようなもの
  即値       42, 16 など          → 数字そのもの
  メモリ     [rbp-8] など         → [ ] の中の数を「住所」として、その番地の中身
  ※ [ ] があるときだけメモリを読み書きする

【主なレジスタ(64bit)】
  rax       計算結果・関数の戻り値
  rdi rsi rdx rcx r8 r9   関数の第1〜第6引数
  rsp       スタックのいちばん上(一番小さいアドレス)
  rbp       関数の基準点(ローカル変数は rbp-8, rbp-16 ...)

【よく使う命令】
  mov A, B     A = B
  add A, B     A = A + B
  sub A, B     A = A - B
  imul A, B    A = A * B
  push A       rsp -= 8; [rsp] = A
  pop A        A = [rsp]; rsp += 8
  call f       戻り先をpushして、fへジャンプ
  ret          戻り先をpopして、そこへジャンプ

■ ステップ1:整数1個をコンパイルする

【作ったもの】(9cc/ フォルダに3つとも置く)
・9cc.c    コンパイラ本体。引数の数字を返すアセンブリを出力する
・test.sh  入力ごとに「期待する終了コード」になるかを自動で確かめる
・Makefile make でビルド、make test でテスト、make clean で掃除

【9cc が出力するアセンブリ】
  .intel_syntax noprefix   Intel記法で書く宣言。noprefix=レジスタに % を付けない
  .globl main              main をリンカ(外)から見えるようにする
  main:                    ラベル。命令ではなく、次の行の場所に名前を付けるだけ
    mov rax, 42            戻り値の置き場所 rax に 42
    ret                    起動用コードに戻る
・終了コードが42になる流れ
  mov rax, 42 → ret で起動用コードに戻る → 起動用コードが rax を使って
  exit(42) → 終了コード → echo $? で見える
・プログラムは main から直接始まるのではなく、Cの起動用コードが main を呼ぶ。
  だから .globl が必要(ないとリンク時に main が見つからないエラー)

【9cc.c で出てきたもの】
  char * = 文字列、char ** = 文字列の配列
・fprintf
  file + printf。出力先を指定できる printf
  printf(...) と fprintf(stdout, ...) は同じ
  fprintf(stderr, ...) で標準エラー出力へ、fopen したファイルにも書ける
・stderr(標準エラー出力)
  プログラムが最初から持っている3本の出入口の1つ
    stdin  (0) 入力   普段はキーボード
    stdout (1) 出力   普段は画面
    stderr (2) エラー 普段は画面
  > は stdout だけを切り替える。だからエラーを printf で出すと
  tmp.s に混ざって画面に出ない → fprintf(stderr, ...) を使う
  確認:./9cc > tmp.s ; cat tmp.s(エラーは画面、tmp.s は空)

【シェルの文法】
・./tmp  「今いるフォルダの」tmp を実行。./ がないと決まった場所しか探さない
・echo   表示する
・$?     直前のプログラムの終了コード
         0〜255 しか表せない(256以上はテストに使えない)
         0 が成功、0以外が失敗(Unixの決まり)
・コマンドのつなぎ方
    A ; B   A が終わったら B(成否は関係なし)
    A && B  A が成功したときだけ B
    A || B  A が失敗したときだけ B
    A | B   A の出力を B の入力に渡す(パイプ)
  ./tmp ; echo $? が ; なのは、42 は「失敗」扱いでも表示したいから
  make && make test は、ビルド失敗時に古い9ccでテストしないため
・> は上書き、>> は末尾に追記(同じ >> を2回やると2回追記される)

【.sh(シェルスクリプト)】
・ターミナルで打つコマンドを順番に書き並べたファイル。上から1行ずつ実行される
・1行目 #!/bin/bash(シバン):bash で実行するという指定。必須
・chmod a+x test.sh:実行してよいという許可を付ける(a=全員、x=実行)
・拡張子 .sh は慣習。人が見て分かるように付けているだけ

【test.sh の中身】
・assert() { ... }  関数の定義。呼ばれたときに動く
・$1, $2            関数に渡された1つ目、2つ目の引数
・expected="$1"     = の両側にスペースを入れてはいけない
・"$input"          変数の中身を取り出す
・actual="$?"       ./tmp の直後に書く(間に別コマンドがあると上書きされる)
・if [ "$actual" = "$expected" ]; then
    [ の後と ] の前にスペース必須。ここの = は比較
・fi                if の終わり(if を逆から)
・exit 1            失敗したらスクリプト全体を終了コード1で止める
                    → make test も失敗 → GitHub Actions で赤くなる

【Makefile】
・形   作りたいもの: 必要なもの
       <タブ>実行するコマンド
・CFLAGS=-std=c11 -g -static
    -std=c11  C11 規格でコンパイル
    -g        デバッグ情報を付ける(gdb で何行目か分かる)
    -static   ライブラリを全部実行ファイルに入れる(macOSが対象外の理由)
・9cc: 9cc.c
    コマンドがなくても、make が .c → 実行ファイルの作り方を知っている
    実際は cc -std=c11 -g -static -o 9cc 9cc.c が実行される
    更新日時を比べて、9cc.c が新しいときだけビルド
    変更がないと「'9cc' is up to date」
・test: 9cc
    先に 9cc を最新にしてから ./test.sh。make test だけでビルド→テストまで
・clean
    rm -f 9cc *.o *~ tmp*
    -f=ファイルがなくてもエラーにしない、*~=エディタのバックアップ
・.PHONY: test clean
    test と clean はファイル名ではなく作業名だと宣言
    ないと「test」というファイルがあるときに、テストが実行されなくなる
■ ステップ2:加減算

【できるようになったこと】
・./9cc "5+20-4" のように、+ と - を含む式をコンパイルできる
・出力例(./9cc "10-3+5")
    mov rax, 10   rax = 10
    sub rax, 3    rax = 7
    add rax, 5    rax = 12 → 終了コード12
・最初の数字を読んだら mov、+ を見たら add、- を見たら sub を出力する
  (記号を見た時点で add か sub かが決まり、直後の数字を strtol で読んで1行出力)

【strtol(p, &p, 10)】
・string to long。文字列を整数に変換する
・引数:どこから読むか / 読み終わった位置を書き込む場所 / 何進数か(10)
・戻り値:読んだ数値
・数字でない文字に当たったら止まり、p をその文字の位置まで進めてくれる
・例 "5+20-4"(p=100番地から)
    strtol → 5 を返し、p は '+' の位置(101)へ
    *p で '+' を確認、p++ で 102 へ
    strtol → 20 を返し、p は '-' の位置(104)へ
・なぜ &p か
    Cの関数は引数をコピーして受け取るので、p をそのまま渡しても
    呼び出し元の p は変わらない。p の住所 &p を渡して書き換えてもらう
    char * の住所なので型は char **(argv と同じポインタのポインタ)
・atoi との違い:atoi は「どこまで読んだか」が分からない
  数字1個のステップ1は atoi で足りたが、読み進める必要があるので strtol

【test.sh】
・入力に記号が入るので "5+20-4" のようにクォートで囲む
■ ステップ3:トークナイザ

【できるようになったこと】
・" 12 + 34 - 5 " のように空白が入っていても読める

【トークナイザとパーサ】
・トークナイザ:文字の並びを意味のある単位(トークン)に区切る。空白はここで捨てる
    ' ' '1' '2' ' ' '+' ... → [12] [+] [34] [-] [5] [EOF]
・パーサ:トークンの並びを読んで、文法どおりか確かめ、意味を読み取る
・コンパイラの流れ
    文字列 ─トークナイザ→ トークン列 ─パーサ→ 構造の理解 ─コード生成→ アセンブリ
・日本語で言えば、トークナイザ=単語に切る、パーサ=文の組み立てを読む


【Cの文法】
・enum:名前付き定数のまとまり。上から 0, 1, 2…
    TK_RESERVED=0(記号)、TK_NUM=1(数)、TK_EOF=2(終わり)
・typedef:型に別名を付ける(TokenKind、Token)
    typedef struct Token Token; を先に書くのは、struct の中で Token *next と
    自分自身の型を使いたいから
・struct:複数の変数をひとまとめにした型
    kind(種類)/ next(次のトークン)/ val(数のとき、その値)/ str(入力の中の位置)
・連結リスト:next で次々につなぐ。要素数を最初に決めなくていい
・Token *token:今パーサが見ているトークン(グローバル変数)
    token = token->next で1つ右へ
・-> :ポインタが指す struct のメンバを取り出す(token->kind)
・str[0]:str が指す場所の0番目の文字
・calloc:メモリを確保して0で埋める(malloc はゼロクリアしない)

【error 関数(可変長引数)】
・void error(char *fmt, ...)  printf と同じ書き方でエラーを出して終了
・...      任意の数の引数が来る
・va_list ap;  va_start(ap, fmt);  ... の引数を順に取り出す準備(stdarg.h)
・vfprintf(stderr, fmt, ap);  fprintf の可変長引数版
・出力は stderr(tmp.s に混ざらない)
・exit(1) で終了 → 終了コード1 → test.sh や make も止まる

■ ステップ4:エラーメッセージを改良

【できるようになったこと】
・エラーの場所を ^ で示せる
    1+3++
        ^ 数ではありません
    1 + foo + 5
        ^ トークナイズできません

【仕組み】
・user_input:入力文字列の先頭(main で tokenize より前に user_input = argv[1])
・error_at(loc, fmt, ...):loc はエラーが起きた位置
・pos = loc - user_input
    ポインタどうしの引き算 = 間に何個要素があるか = 先頭から何文字目か
    例:user_input=100番地、loc=104番地 → pos=4
・fprintf(stderr, "%*s", pos, " ")
    %*s は幅を引数で指定する書式。" " を幅 pos で出す → 空白が pos 個
・場所が分かるのは、トークンの str が入力文字列の中を指しているから(ステップ3の設計)
  exit(1) はエラー後に続けても意味がないから止めるだけで、場所が分かる理由ではない

■ GitHub Actions

【何をするか】
・プッシュするたびに、GitHub が新品の Ubuntu を用意して make test を実行
・結果がコミットの横に ✅ / ❌ で表示される

【うれしい点】
1. 外部の人がコードを動かさなくても、テストが通っていると分かる
2. 毎回まっさらな環境で動くので「自分のPCでしか動かない」を防げる
3. 前のテストを壊したらすぐ気づける
