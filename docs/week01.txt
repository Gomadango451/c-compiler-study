②コンパイルの4段階とgccの最適化
================================
日付: 2026-10-18(第1週)

■ 使ったソース (hello.c, 11行)
  #include <stdio.h>
  int add(int a, int b) { return a + b; }
  int main(void) { int x = add(3, 4); printf("%d\n", x); return 0; }

■ 全体の流れ
hello.c →(-E)→ hello.i →(-S)→ hello.s →(-c)→ hello.o →(リンク)→ hello
 Cの原文    展開後のC    アセンブリ     機械語       実行ファイル
自作コンパイラが担当するのは「hello.i から hello.s を作る部分」。

■ 段階1: 前処理 (gcc -E hello.c -o hello.i)
- #include や #define など「#」で始まる行を処理する。テキスト置換のみ。
- hello.c 11行 → hello.i 824行。増えた分は stdio.h の中身。

■ 段階2: コンパイル (gcc -S -masm=intel -O0 hello.c -o hello_O0.s)
- Cのコードをアセンブリ(テキスト)に変換する。狭い意味の「コンパイル」。
- -masm=intel はIntel記法で出力する指定(植山本もこの記法)。
- add関数 (-O0):
    push rbp / mov rbp, rsp      関数の入り口の定型句(スタックフレーム作成)
    mov [rbp-4], edi             第1引数aをスタックに保存
    mov [rbp-8], esi             第2引数bをスタックに保存
    mov edx, [rbp-4] / mov eax, [rbp-8]   スタックから読み戻す
    add eax, edx                 足し算の本体
    pop rbp / ret                入り口の逆。呼び出し元に戻る
- 戻り値は eax に入れる規約。
- x86-64の引数渡し: 第1引数 edi(rdi)、第2引数 esi(rsi)。
- main関数: mov esi,4 / mov edi,3 / call add で呼び出し。
  戻り値(eax)を x の置き場 [rbp-4] に保存。
  printfは第1引数(書式文字列)を rdi、第2引数(xの値)を esi にセットして呼ぶ。

■ 段階3: アセンブル (gcc -c hello.c -o hello.o) と objdump
- アセンブリを機械語(バイナリ)に変換する。
- objdump -d -M intel hello.o で逆アセンブルして読む。
- 例: 機械語 55 の1バイトが push rbp。
- アセンブリ1行と機械語はほぼ1対1で対応する。
- call の行き先は 00 00 00 00 のまま。add や printf の場所はまだ未確定。

■ 段階4: リンク (gcc hello.o -o hello)
- ライブラリ(printfなど)を結びつけ、call の行き先を確定して実行ファイルにする。
- ./hello で 7 と表示された。(./ は「今いるディレクトリの」の意味)
- 前の行が成功したときだけ次を実行したいときは && でつなぐ。

■ -O0 と -O2 の比較
- -O0: 書いたとおりに素直に翻訳する。読みやすい。
- -O2: 意味を保ったまま、書いていない形に書き換える。
- add関数: -O0は9命令前後 → -O2は2命令 (lea eax,[rdi+rsi] / ret)。
  引数をスタックに保存せずレジスタのまま使う。rbpのフレームも作らない。
- main関数: add の呼び出しが消え、7 を直接 printf に渡す。
  これは「定数畳み込み」(コンパイル時に 3+4=7 を計算する最適化)。
  引数が両方定数だから可能。実行時にしか分からない値は畳み込めない。
- その他: printf → __printf_chk(Ubuntuの安全強化 _FORTIFY_SOURCE による置き換え)、
  mov eax,0 → xor eax,eax(同じ意味でより短い)。
- 自作コンパイラが最初に作るのは -O0 に近い出力。
  理由: 構文木をたどって機械的にコードを出せる。最適化は正しさを保つのが難しいので後回し(第16週)。

■ 補足: ヒアドキュメント
  cat > hello.c << 'EOF' ... EOF
  「EOFの行が来るまでの内容をファイルに書き込む」シェルの機能。
  'EOF' とクォートすると $ や ` をシェルが解釈しない。EOFは行頭に書く。

③スタックとスタックフレーム
================================
日付: 2026-10-18(第1週)

■ スタックとは
- 関数呼び出しなどで使う作業台。後入れ先出し(LIFO)で、順番にしか取り出せない。
- x86-64ではスタックは小さい番地の方向(下)へ伸びる。

■ レジスタ
- rsp (Stack Pointer): スタックの先頭を指す。push/pop/call/ret で自動的に動く。
- rbp (Base Pointer) : 関数の足場の基準。その関数の間は動かさない。
  変数を [rbp-4] のように固定の相対位置で指定できる。
- rax: 戻り値、計算結果 / rdi: 第1引数 / rsi: 第2引数
- 先頭の r は64bit、e は32bit(eax)、ax は16bit、al は8bit。

■ プロローグとエピローグ
- プロローグ(関数の最初): 足場を作る
    push rbp        呼び出し元の rbp をスタックに退避
    mov rbp, rsp    今の rsp を、この関数の足場の基準にする
- エピローグ(関数の最後): 後片付け
    pop rbp         退避していた rbp を戻す
    ret             戻り先アドレスを取り出してジャンプ

■ 保存されるものの区別(間違えやすい)
- 戻り先アドレス: call が自動で積む。ret が取り出す。
- 呼び出し元の rbp: 関数自身が push rbp で積む。pop rbp で戻す。
  理由: mov rbp, rsp で rbp を書き換えるので、元の値を失わないため。

■ add実行中のスタック(上が大きい番地)
  main の戻り先
  保存された呼び出し元の rbp   ← main の rbp
  main の作業領域(sub rsp,16)
  add の戻り先                 ← main の call add が積む
  保存された main の rbp       ← add の push rbp  ← rsp, rbp
  [rbp-4] = a = 3
  [rbp-8] = b = 4              ← rsp より下に書かれている

■ 呼び出しから戻るまでの変化
  A. main: sub rsp,16        main の作業領域ができる
  B. call add                add の戻り先が積まれる
  C. push rbp                main の rbp が保存される
  D. mov rbp, rsp            add の足場の基準が決まる
  E. mov [rbp-4], edi など   a=3, b=4 を書き込む
  F. pop rbp                 rbp が main の値に戻る
  G. ret                     戻り先を取り出して main に戻る
- 積んだものを逆順にすべて取り出して、元の状態に戻る。
- call と ret、push rbp と pop rbp は、それぞれ対になっている。

■ 植山本の方式: スタックを計算の作業台にする
- 式は push / pop だけで評価する。
- 型: 左辺を計算して push → 右辺を計算して push →
      pop rdi (右辺) → pop rax (左辺) → 演算 → 結果を push
  例: (1 + 2) * 3
    push 1
    push 2
    pop rdi        右辺
    pop rax        左辺
    add rax, rdi
    push rax       結果を積み直す
    push 3
    pop rdi
    pop rax
    imul rax, rdi
    push rax       最終結果(9)
- 結果を必ず push する理由:
  1. 全ての演算が「2つ pop して1つ push」という同じ型になり、コード生成が単純になる。
  2. rax や rdi は次の計算で上書きされる。
     例: (1+2)*(3+4) で、左の結果を rax に置いたままだと右の計算で消える。
     スタックなら、後の計算に壊されない。
- 取り出す順は固定: pop rdi が先(右辺)、pop rax が後(左辺)。
  足し算・掛け算では順序は無関係だが、引き算・割り算では結果が変わる。
    push 3 / push 20 / pop rdi / pop rax / sub rax, rdi  →  3 - 20
- 構文木を後行順走査(左→右→演算)でたどると、この出力になる。
- 効率は gcc -O0 より悪いが、レジスタ割り当てを考えずに済むので最初に作りやすい。


④用語の整理(インタプリタ・クロスコンパイル・ブートストラップ・セルフホスト)
================================
日付: 2026-10-18(第1週)

■ 32bitと64bitの呼び出し規約
- 32bit x86(cdecl): 引数はすべてスタックに積む(右から左)。
  第1引数は [ebp+8]。理由: [ebp+4]=戻り先(4バイト)、[ebp+0]=保存したebp(4バイト)。
- 64bit x86-64(System V ABI): 引数はレジスタで渡す。
  第1〜第6引数: rdi, rsi, rdx, rcx, r8, r9(暗記済み)
  7個目以降はスタック。戻り値は rax。
- 64bitの利点: メモリへの読み書きが減って速い。汎用レジスタが8本から16本に増えた。
- 授業(32bit)と植山本(64bit)で違うが、スタックフレームの仕組みは共通。

■ インタプリタとコンパイラ
- コンパイラ: 全体を機械語に変換してから実行する。速い。(C, Rust, Go)
- インタプリタ: 1行ずつ読んで、その場で解釈して実行する。遅い。
- 境界はあいまい。Python/Javaは中間コード(バイトコード)に変換して仮想マシンで実行。
  JavaScript(V8)は、よく使う部分だけ実行中に機械語にする(JIT)。

■ クロスコンパイル
- 動いているマシンとは別の種類のマシン向けにコンパイルすること。
- ホスト: コンパイルを行うマシン。ターゲット: 実行ファイルを動かすマシン。
- 例: x86-64のPCで、ARM(スマホ、Raspberry Pi)向けの実行ファイルを作る。
- 通常の gcc hello.c は、ホストとターゲットが同じ。

■ ブートストラップ
- 自分を作るために、まず自分より単純なものを使うこと。
- コンパイラでは、最初は別の言語で小さなコンパイラを作り、
  それで少しずつ大きなコンパイラをコンパイルして成長させる。

■ セルフホスト
- コンパイラが、自分自身のソースコードをコンパイルできる状態。
- 自作コンパイラのソースもただのCプログラム。関数、ポインタ、構造体、enumなどを使っている。
  自分を処理できる = それらの機能を正しく処理できる、ということ。
- 第1世代(gccでコンパイル)と第2世代(自作コンパイラでコンパイル)の出力が一致すれば、
  実装が正しいことの強い確認になる。
- 植山本の当面の目標はセルフホスト。
  私たちの計画では、第16週のゴールは8クイーン。セルフホストは2〜4月の拡張候補。
